# QA Shop assertion issuer

Local candidate only. Do not deploy without separate approval. This Worker serves only `POST /api/shop/session-assertion` for Firebase project `adischat-qa`; it is not the production AdisChat bridge.

Required configuration names: `FIREBASE_PROJECT_ID`, `QA_FIREBASE_WEB_API_KEY`, `ADISHOP_ASSERTION_ISSUER`, `ADISHOP_ASSERTION_AUDIENCE`, `ADISHOP_ASSERTION_SECRET`, `QA_RATE_LIMITER`, `QA_ALLOWLIST_READER`, and `QA_ALLOWLIST_READ_SECRET`. The project, issuer and audience are pinned in source. The Web API key, assertion secret, and independent 48-byte-or-longer allowlist-read secret belong in protected Worker secret management. The issuer has **no D1 binding**; the private reader owns the sole allowlist SELECT operation. Use the existing staging-only assertion secret that matches staging exchange verification; never copy a production signing secret. Do not put secrets in this directory or in Wrangler vars.

The Worker validates RS256 Firebase tokens against Google's public keys, checks the QA project claims, and calls Firebase `accounts:lookup` with the caller's token to reject disabled or revoked accounts. It signs a two-minute assertion for the verified UID only. Firebase lookup and rate-limit errors fail closed. The binding limits pre-verification work by Cloudflare-provided client IP (or one shared unknown key) and signed requests by UID. These limits are per location, approximate, and cannot replace Cloudflare edge/WAF limits for unauthenticated floods; a strict global limiter would require separately approved infrastructure. No administrative routes are exposed.

Deploy the private `adischat-qa-allowlist-reader` before the issuer in any separately approved staging rollout. Its `workers_dev = false` template has no public route; preview/version URLs still need the HMAC check. The reader has the QA D1 binding but exposes only signed membership lookup. The revoker keeps its separate administrative D1 binding. A compromised reader or revoker can still write D1; this separation removes D1 capability from the issuer, not from the entire QA system. Hosted binding and access checks remain required.

Before separately approved deployment, create disposable Firebase QA accounts and matching staging Shop profiles/identity links with provider `firebase` and the same verified Firebase UID. Assign buyer, seller and admin roles server-side, including suspended fixtures. The six existing `staging-auth:` Supabase fixtures cannot be relinked as Firebase QA users. Configure Android `QA_IDENTITY_BRIDGE_URL` to the dedicated Worker URL only after the QA isolation gate accepts every service endpoint. Do not enable order mutations or payments for these tests.

Verification: run `node --test cloudflare/qa-shop-issuer/src/index.test.mjs`; then, after approval and deployment, use genuine disposable Firebase QA tokens to check active exchange/refresh, suspended and revoked denial, replay, and role boundaries. Inspect only status codes and synthetic fixture IDs, not tokens. Cleanup means revoke Shop session families, disable/remove disposable identity links and accounts through supported Admin workflows, clear the Worker allowlist and secrets, and remove the Worker after tests. Preserve staging exchange/refresh functions and audit records.

## Identity lifecycle handoff (proposal, not deployed)

The Worker controls new assertion issuance only. Firebase disable, token revocation, or UID allowlist removal must also invoke a staging-only, privileged Shop revocation operation. That operation must resolve the profile from the server-verified Firebase UID, lock the profile/link and session families in the established rotation order, mark all active families and sessions revoked idempotently, and append an audit event. It must not accept a caller-supplied profile ID or role as authority. A failed Firebase-to-Shop propagation remains pending for retry and reconciliation; do not report the identity disabled end-to-end until Shop revocation is confirmed. Reconcile Firebase disabled/revoked users and the allowlist against active Shop families periodically, using synthetic staging identities only. Existing profile/link suspension triggers already revoke families; verify their deployed parity before relying on them. Logout should revoke the captured family, then clear local credentials; if server revocation fails, retain a retry signal rather than claiming global logout. Race tests must cover revocation before/after rotation, concurrent exchange, repeated revocation, and subsequent access-token denial. No hosted revocation connector or additional RPC is part of this candidate.
