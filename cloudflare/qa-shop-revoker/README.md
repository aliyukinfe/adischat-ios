# SEC-03H QA revocation coordinator (local candidate)

This is not deployed. The SEC-03J runtime entry is `src/delivery.mjs` and `workers_dev = false`; a separately approved, Cloudflare Access-protected route is required. It accepts only a signed Access **service-token application JWT** for the exact QA audience and service-token ID. Cloudflare Access must deny every other principal before the Worker. No Android client calls this endpoint. The SEC-03H `src/index.mjs` handler remains as a local test interface, but the deployment entry does not route to its offset-based scanner.

The authorized caller supplies a stable operation ID, Firebase UID selector, and action. The UID is not an authority: the Worker verifies the Access token, obtains QA-only Firebase Admin credentials, looks up the user in `adischat-qa`, and resolves the staging Shop link. A D1 intent is recorded **before** Firebase mutation. The Google Identity Platform `projects.accounts.update` API disables the user or advances `validSince`; only after verified readback does the Worker queue a signed event. HTTP 202 means pending Shop revocation, not completed. The Queue consumer checks the HMAC, D1 operation, Firebase state and Shop link before calling the service-role-only SEC-03H event RPC. It acknowledges only a confirmed result. The event ledger and SEC-03G function revoke families/sessions atomically and make retries idempotent.

## Event delivery

| Event | Delivery and authority | State |
| --- | --- | --- |
| Firebase user disabled | Trusted QA admin calls `/api/shop/identity/admin-change`; D1 intent, Firebase update, Queue, then Shop RPC. Reconciliation discovers Console-side changes. | Local implementation; no hosted verification. |
| Firebase tokens revoked | Same path, advancing `validSince`. Equal-second pre-mutation boundaries wait; uncertain post-mutation recovery requires review. Reconciliation conservatively revokes ambiguous active families. | Local implementation; hosted semantics unverified. |
| QA allowlist removal | Issuer and revoker query the same proposed QA D1 allowlist; a removed UID cannot get new assertions, and reconciliation revokes existing Shop sessions. | Local implementation; D1 resource and removal administration not provisioned. |
| Shop profile suspension or identity-link disablement | Existing Stage 3 database triggers revoke families/sessions in the same transaction. | Existing SQL behavior, not delivered by this Worker. |
| Explicit logout | Existing Android Shop revoke/family endpoint is user-initiated. It is not an administrative revocation event. | Existing behavior; logout failure while offline remains a separate gap. |

Firebase does **not** automatically deliver every administrative or Console-side change. The local producer owns QA disable/revoke requests; Console changes are detected by scheduled reconciliation. D1 records operations before external mutation. After Firebase success plus Queue failure, the operation remains `firebase_done` and a scheduled outbox resend requeues the same ID. The consumer retries transient failures; configured Queue exhaustion sends messages to a separate DLQ for operator inspection. Invalid signed events are sent to a separate quarantine queue before acknowledgement. Five enqueue attempts are the local outbox cap; `attention=delivery-exhausted` requires an operator. No event or credential body is logged.

Reconciliation scans at most 8 links per hosted invocation, ordered by link UUID with `id=gt.<cursor>`. D1 persists the cursor, lease and sanitized failure category; it resets only after reaching the end. A failed page does not advance. It compares Firebase disabled/`validSince`, the shared allowlist, Shop profile/link state and active families. SEC-03G revokes Firebase/allowlist cases; the separate SEC-03J service-role RPC revokes stray families for inactive Shop profiles/links. Reconciliation never reactivates an identity. A same-second `validSince`/family boundary is ambiguous and is **conservatively revoked**, counted as `ambiguous`; this is not proof of event order. Missing Firebase users or unavailable dependencies stop the page and require operator action.

## Staging-only prerequisites

- Cloudflare Access service-token application, exact audience and client ID, no public route, restricted route/WAF request limit.
- QA Firebase service account with `firebaseauth.users.get` and `firebaseauth.users.update` permissions in `adischat-qa`; keep JSON in Worker secret storage.
- Staging `sb_secret_` key in Worker secret storage, sent only on `apikey`, never as a bearer token.
- One QA-only D1 database with `qa-state-schema.sql`, bound as `QA_STATE_DB` to the revoker and the private `adischat-qa-allowlist-reader`, **not** the issuer. The issuer has only a service binding to the reader. Provision independent `QA_ALLOWLIST_READ_SECRET` in issuer and reader secret stores. An authorized QA admin must populate only verified QA Firebase UIDs; missing data denies issuance. Neither Android nor production receives the D1 binding.
- Two producer Queue bindings, `QA_REVOCATION_QUEUE` and `QA_INVALID_QUEUE`; one consumer with a distinct DLQ; `QA_ADMIN_RATE_LIMITER`; a one-minute Cron trigger. See `wrangler.qa.example.toml`. These are placeholders, not created resources.
- Worker variables: `QA_FIREBASE_PROJECT_ID`, `QA_SHOP_URL`, `QA_ACCESS_TEAM_DOMAIN`, `QA_ACCESS_AUD`, `QA_ACCESS_SERVICE_TOKEN_ID`.
- Worker secrets: `QA_FIREBASE_SERVICE_ACCOUNT_JSON`, `QA_SHOP_SERVICE_ROLE_KEY`, `QA_EVENT_HMAC_SECRET` (independent random 48+ bytes). The issuer retains its separate assertion secret and QA Firebase Web API key.
- Apply SEC-03G revocation SQL after Stage 2 and Stage 3 guards, then SEC-03H event ledger and SEC-03J inactive-session candidate; verify grants, RLS and audit.
- No production Worker, Firebase project, Android app, or Supabase project is a target.

**Approval gates:** (1) backup and verify exact staging Supabase project; (2) review/apply only the three narrow SQL candidates; (3) approve QA D1, Queue/DLQ/quarantine, Access, limiter and Cron resources with cost/retention review; (4) provision secret names through secure management; (5) deploy revoker and issuer using reviewed bundles and exact QA bindings; (6) create disposable Firebase QA users and Shop links; (7) run hosted Access, Firebase mutation, Queue retry/DLQ, PostgREST RPC, refresh/revocation race, allowlist removal and full reconciliation tests. Stop at any failed gate. On incident, disable Access route and issuer, keep SQL session guards and audit ledger, preserve D1/Queue evidence, and use a reviewed forward fix. Never roll back to a vulnerable identity function.

**Still unverified:** Cloudflare Access, service binding and D1 hosted behavior, Firebase `validSince` precision and REST update semantics, staging PostgREST grants/API exposure, Free-plan CPU/subrequest budgets, queue retention and DLQ alerts. The issuer's D1 binding has been removed locally; reader and revoker retain D1 write capability, so their code, deployment bindings and administrative access need review. No automatic Console event hook exists. A processing operation whose Firebase update outcome is ambiguous is deliberately left pending for manual review; never repeat token revocation blindly.
